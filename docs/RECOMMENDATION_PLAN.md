# LookingFor 推荐算法优化计划

日期：2026-10-23。代码基线：`adb6b14`。

**状态：待实施。** 本次只更新文档，没有修改线上推荐算法，也没有完成用户实验。下面的收益是待验证假设，时间是工作量估计。

目标是让前几屏出现更多与当前用户有关、值得打开的仓库，同时保留旧收藏的重新发现价值。Star 数少不能证明算法失败；算法改善也不能保证项目获得更多 Stars。

## 1. 代码里实际存在的问题

| 位置 | 当前行为 | 优化要解决什么 |
|---|---|---|
| [analyse.py](../analyse.py) 的 `_profile_keywords` / `generate_search_keywords` | 模型输出兴趣、理由、证据仓库，但返回值只剩扁平关键词；分批结果按调用顺序拼接再截取前 80 个 | 保存兴趣与证据关系，避免前面的输入批次占满搜索预算；区分明确兴趣和相邻探索 |
| [database.py](../database.py) 的 `analyses` | 只持久化 `keywords_json` 和收藏版本 | 无法从保存的结果还原用户兴趣，也无法追溯某条推荐的依据 |
| [search.py](../search.py) 的 `fetch_repositories` | 所有查询均为 `sort=stars&order=desc`，每页 10 条 | 热门项目优先进入候选池；重排无法选中根本没有被搜索到的项目 |
| [discovery.py](../discovery.py) 的 `load_more` | 一个结果会被附上整个 OR 查询组的所有关键词 | 这是查询来源，不能当作真实匹配词数。例如 `A OR B OR C OR D` 返回的项目不一定同时匹配四个词 |
| [views.py](../views.py) 的 `repository_browser` | 批内按上述词数、Star 数排序 | 排名受查询分组长度和重复召回影响；同一候选再次出现还可能改变之前批次的顺序 |
| [search_guard.py](../search_guard.py) 的 `cache_key` | 缓存签名固定包含 `stars`、`desc`，公用缓存只存公开结果 | 未来若支持不同排序或响应格式，必须同步更新缓存键，不能串用缓存；个性化评分也不能写进公共缓存 |
| [tests/](../tests/) | 验证流程正确性，尚无推荐质量评估集 | “程序能跑”和“推荐有用”需要分别验证 |

当前系统已有分页、去重、查询组轮转、限流和后台任务。保留这些基础，逐段改进推荐流程。

## 2. 范围和约束

- 第一版使用 Python，沿用 SQLite、Redis、NiceGUI；可以增加 scikit-learn 做离线文本基线，不需要 GPU、向量数据库或训练服务。
- 保留现有 Star 降序搜索作为基线和一个候选来源。第一轮新增查询仍可以使用相同的 `sort` / `order`，通过更具体的主题和热度区间扩大覆盖。
- **已 Star 的仓库继续参与推荐。** 是否收藏、是否看过、是否有用是三个不同字段；没有 Star 不等于从未见过。
- 大模型继续负责兴趣提炼。先使用这次调用已产生的信息，不为每个候选额外调用一次模型。
- 保持现有 API 限流、查询锁、失败重试和用户隔离。一次“继续发现”的外部查询预算先保持不变。
- 这一阶段不重做网站、不训练协同过滤、不抓取全 GitHub、不根据 GitHub Star 总数判断产品成败。

建议流程：

```text
Stars 快照
  → 有证据的兴趣档案
  → 按兴趣分配有限查询预算
  → 多个查询来源取得公开候选
  → 实际文本 / topic 相关性评分
  → 减少同类结果扎堆
  → 输出可追溯的理由和稳定的下一批结果
```

## 3. 分阶段实施

### P0：固定基线和评价方式（1–2 个工作日）

先保存一份可重放的输入和当前结果，之后的权重、prompt 和检索方式才能公平比较。

1. 用自己的账号建立第一个案例，记录收藏快照版本、生成关键词、查询参数、公开响应、批次与显示顺序、请求时间和缓存状态。禁止记录 token。
2. 创建 `evaluation/` 下的案例格式与离线回放方式。先有一个端到端案例，再邀请 3–5 位愿意参与的不同兴趣用户；未取得同意的用户数据不用于评估或提交到 Git。
3. 每个案例先人工判断约 30–50 个候选。候选池合并基线、新方法的靠前结果，以及少量随机抽样，去重后隐藏算法来源再评价。新方法的前 10 个结果必须补齐标注，不能把未标注结果自动当作不相关。
4. 每个仓库记录：相关性 `0=无关 / 1=有一定关系 / 2=明显相关`、是否以前见过、是否值得打开、是否值得重新发现。已收藏的项目不能自动得到最高相关性分。
5. 固定开发集和留出的验证案例；只在开发集调参数，验证集用于最后比较。样本少时报告逐用户结果，不声称统计显著。

**验收：** 相同快照和候选数据能离线得到完全相同的基线顺序；形成第一份人工判断表。还没有真实标签时，只报告覆盖、重复等诊断数据，不声称相关性提升。

### P1：保存兴趣证据，修正查询来源的含义（2–3 个工作日）

修改 `analyse.py`、`analysis_jobs.py`、`database.py`、`discovery.py`，并小幅调整结果卡片文案。

- 新分析结果包含 `interests`、`evidence_repos`、`search_keywords`、`exploration_directions`、`uncertainties`，保留旧关键词接口作为兼容层。
- 校验 JSON 的字段类型、长度、引用关系；证据仓库必须存在于该用户实际送给模型的输入中。`evidence_strength` 是模型判断，不是校准过的概率。
- 分批输出先按规范化关键词和去重证据合并确定相同的兴趣，无法确定的保持独立；查询配额按兴趣轮转，不直接把第一个输入批次的关键词优先塞满 80 个位置。
- 在分析表中增加可空的结构化结果和版本字段，迁移保留旧数据。旧用户没有新档案时继续使用关键词基线，不在启动时批量重新付费分析。
- 保存 `schema_version`、`prompt_version`、模型标识及实际分析输入摘要；沿用收藏版本检查，避免过期后台任务覆盖新快照。
- 用 `retrieval_sources` 记录查询、兴趣 ID、页码、排序方式和原始名次；把实际文本或 topic 匹配另存为 `match_evidence`。来源数量不再冒充匹配词数。
- 中英文卡片在有真实证据前只写“搜索来源 / Search source”，不生成“因为你喜欢……”的猜测句。

**验收：** 虚构证据被拒绝或移除；改变 OR 组长度不再凭空增加相关性；旧数据能读取；过期结果、并发去重、跨用户隔离测试仍通过。此阶段使用原搜索顺序作为临时展示基线，单独记录排序变化。

### P2：扩大候选覆盖，保持请求预算（2–3 个工作日）

增加 `retrieval.py` 管理查询计划，让 `search.py` 继续负责请求，`search_guard.py` 继续负责保护。GitHub 支持 `topic:`、`stars:` 区间和 `in:` 等限定，适合做有限的查询组合。[GitHub 仓库搜索语法](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)

| 来源 | 第一轮实验 | 用途 |
|---|---|---|
| 现有来源 | 保留当前关键词组、Star 降序 | 作为比较基线和热门相关项目的来源 |
| 具体主题 | 用证据仓库的真实 topic，或较短的功能关键词，仍按 Star 降序 | 检验长英文短语是否漏掉相关仓库，减少多个不相关兴趣被拼成一组 |
| 分段探索 | 在具体兴趣查询中加入不同 Star 数区间，区间内仍降序 | 给头部项目以外的候选进入池子的机会 |

- 先维持每次最多 4 次搜索、每页 10 条，在来源和兴趣之间分配配额；不足的来源把配额让给其他来源。没有标注证据前，不把配额比例定为“最优”。
- 低 Star 数不代表高质量，不给所有小项目统一加分。区间阈值由候选分布决定，并做对照实验。
- 查询计划有有限的组合数、页数和请求预算；不能为绕过搜索上限无限生成查询。每条查询保留独立进度、失败重试和结束原因。
- GitHub 每次搜索最多可访问 1,000 条结果；结果不完整、限流和没有更多结果必须分别处理。[GitHub Search API](https://docs.github.com/en/rest/search/search#search-repositories)
- 查询参数和缓存签名必须共用同一份配置。若以后测试 best-match 或更新排序，同时把 `sort`、`order`、`per_page`、API/响应格式版本纳入缓存键；不要只改请求。
- 公共 Redis 仍只缓存原始公开候选。用户兴趣、得分、已收藏状态和解释只在用户级流程生成；若缓存，键必须包含用户、快照与算法版本。

**验收：** 在相同请求预算下比较有用候选数量、重复率、兴趣覆盖、错误率和延迟。通过历史响应离线回放后，再做少量真实 API 检验；不能只看 mock 测试。小众结果更多但更不相关的方案不算成功。

### P3：建立轻量排序与证据解释（2–3 个工作日）

增加 `ranking.py`，保持为可离线调用的纯 Python 评分模块。输入是兴趣档案与候选；输出是仓库 ID、得分、匹配兴趣和理由证据。

**第一组实验：固定同一候选池，只改变排序。**

1. 基线 A：复现旧版“来源关键词数 + Stars”顺序，用于比较。
2. 基线 B：用兴趣证据仓库的描述、topics 和英文关键词表示每个兴趣，候选使用自己的描述、topics 和名称；先用 TF-IDF 加余弦相似度。对每个候选取最相关的兴趣，避免把所有兴趣平均成一个模糊向量。可用 [TfidfVectorizer](https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html) 与 [cosine_similarity](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.pairwise.cosine_similarity.html) 实现。
3. 基线 C：在 B 上加真实 topic 重合。先比较纯文本与“文本 + topic”两个版本，再调少量权重。Python/JavaScript 等语言仅作辅助信号；想使用一个工具，并不意味着只喜欢自己会写的语言。
4. 候选若已在收藏里，计算相似度时排除它自身作为证据，避免复制自己的描述得到满分。仍然允许其他兴趣证据把它推荐回来。
5. Star 数保留展示，最多在相关性相近时作次级排序。归档、缺失描述和长期未更新分别记录，不把“最近 push”当作维护质量的充分证据，也不一刀切淘汰稳定工具。

词汇相似度不能理解所有同义词或中英文对应。先比较字符与词级特征、记录失败案例；如果主要错误确实来自语义差异，再用同一评估集测试 embedding。此时才选模型、测内存与延迟，不先搭向量数据库。

**第二组实验：相关性足够之后再增加多样性。**

- 从相关候选中逐个选择，降低与已选项目高度相似的候选优先级，或限制单一兴趣占满首屏。每个参数都与不做多样性的版本比较。
- 已 Star 和未 Star 都可被选中。分别统计两类结果的有用程度；不硬设必须多少未 Star，也不为“冷门”牺牲相关性。
- 评分并列用稳定仓库 ID 决定顺序。首次与下一批使用同一评分函数，但已经显示的批次不随新候选到来重新洗牌。

**解释只从证据拼接：** 例如“与你收藏的 A 具有共同 topic：T”；A 必须在用户快照中，T 必须在双方元数据中。只有文本相似时写清“描述相近”；没有具体证据就只标兴趣或搜索来源。不得把计算相似度写成用户明确表达过的喜好。

**验收：** 在相同候选池和冻结评估集上更相关，而不是仅更冷门；缺少描述/topic、只有一条收藏、纯中文、混合语言及并列分数都有确定的处理方式。

### P4：接入页面、验证真实效果（约 2 个工作日，用户试用另计）

- `discovery.py` 维护已展示 ID、候选缓冲区、查询计划和分页游标。下一批先消费缓冲区，再按预算取新候选；不能取回很多候选却丢弃尚未展示的部分。
- `views.py` 使用排序模块给出的顺序，不再重新按词数和 Star 数覆盖；`main.py` 传入当前用户的档案和版本。页面只需改排序来源与理由，沿用现有布局。
- 快照变化、重新分析或退出登录时废弃旧用户的候选状态。跨用户相同公共仓库可以复用抓取结果，但不能复用个性化分数。
- 设置算法开关，在少量自愿用户中试用；旧版作为回退。有限流或无档案时展示明确状态，不能静默把热门列表叫作个性化推荐。
- 可选反馈先限于“相关 / 不相关 / 值得重看”。如记录点击，需同时记录真正可见的曝光、位置、算法版本；未点击不等于不喜欢。更新隐私说明和删除逻辑，再收集反馈。

**验收：** 第一批和连续三批顺序稳定、没有重复展示、刷新/切换用户不会串数据；计费和请求数量有记录；旧版可恢复。现有测试通过，并补充对应回归测试。

## 4. 怎么判断改好了

| 指标 | 用途与边界 |
|---|---|
| `nDCG@10` | 评价相关结果是否排在前面。使用统一、已标注的候选池和相同的 0/1/2 标签；不把未评判结果当负例。参见 [scikit-learn 定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html) |
| 首屏值得打开的数量 | 用户直接判断前 10 个里愿意进一步了解几个；比 Star 总数更贴近本项目目的 |
| 发现价值 / 重新发现价值 | 按“原本知道 / 不知道”“已收藏 / 未收藏”分别报告。只在用户确认以前不知道时称为新发现 |
| 候选覆盖和重复率 | 评价新增查询是否带来有用候选；不是对整个 GitHub 的真实 recall |
| 结果多样性 | 记录前 10 条覆盖的相关兴趣数、同类扎堆情况；兴趣多但无关不能算改善 |
| 请求量、缓存命中、耗时与成本 | 区分冷缓存、热缓存、首次模型分析和已有档案浏览；延迟记录中位数与 p95 |

小样本先给出逐案例前后对比和失败案例，不宣布百分比增长已经具有普遍性。建议初步放量门槛是：验证集平均 nDCG@10 与“值得打开数量”均优于基线、没有明显兴趣组退步、请求预算未增加；若样本不足或结果冲突，继续小范围试用，不扩大宣传。

另做三组消融：只改排序、只改检索、两者一起改。这样才能分清收益来自哪里。若以后使用“隐藏一部分 Stars 再找回来”的测试，必须在生成兴趣、关键词和统计前就移除这些仓库；它仍只是偏好代理测试，不能替代用户对新项目的评价。

## 5. 第一个实现任务

**从 P0 的单案例回放开始，然后实施 P1；暂不改变 API 查询策略。**

第一个代码 PR 的完成条件：

- [ ] 保存一份不含凭据的基线案例和真实判断格式；测试夹具使用合成或允许公开的数据。
- [ ] 保留并校验结构化兴趣结果，兼容旧 `keywords_json`。
- [ ] 把查询来源与真实匹配证据分开，停止按整组词数冒充相关性。
- [ ] 给结果附带算法/输入版本，测试用户隔离、旧任务覆盖防护和稳定顺序。
- [ ] 输出一份基线报告，明确尚未证明排序质量提高。

P0–P4 约需 9–13 个工作日；以学习和兼职节奏进行时，可安排在 3–5 周，真实用户反馈时间另计。优先完成可比较的小版本，再决定是否值得引入 embedding 或更昂贵的模型重排。

token 静态加密和模型费用控制仍属于上线准备事项，与推荐质量分开跟踪。本轮文档没有完成这些改动。这个项目当前能练习检索、排序、评估与模型调用成本控制；它本身不等同于大模型推理内核优化研究。
